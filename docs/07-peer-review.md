## 1. 과제 이해 (5분)

**평가자**: 이 미션을 한 문장으로 설명하면 뭔가요?

**발표자**: 제공된 `agent-leak-app`을 리눅스에서 실행해서 메모리 누수(OOM), CPU 과점유, 교착상태(Deadlock) 세 가지 장애를 재현하고, 관제 데이터와 로그를 근거로 원인을 추론한 뒤, 그 결과를 GitHub Issue 형식의 기술 리포트로 남기는 미션입니다.

**평가자**: 미션 소개에 "로그 없이 재부팅부터 하면 원인이 묻힌다"는 말이 있잖아요. 이게 왜 중요한가요?

**발표자**: 재부팅하면 프로세스의 메모리 상태, 스레드 상태, 마지막 로그 위치 같은 장애 시점의 증거가 다 사라집니다. 원인을 모르니 같은 장애가 반복되고요. 그래서 이 미션은 "고치기"보다 "증거를 남기고 원인을 설명하기"에 무게가 있다고 이해했습니다.

**평가자**: 그럼 "장애 대응을 잘했다"의 기준은 뭐라고 생각해요?

**발표자**: 세 가지입니다.

1. 장애가 어떻게 보였는지 **관측 사실**을 시간 순서대로 제시할 수 있을 것
2. 그 사실에서 **원인을 추론**하고, 관련된 OS 동작 원리로 설명할 수 있을 것
3. 환경변수 하나를 바꿔 **Before & After를 비교**해서 추론이 맞는지 검증할 것

README의 "장애 분석 흐름"에 앱 실행 → 자원 모니터링 → 장애 관측 → 환경변수 변경 → 전후 비교 5단계로 정리했고, 단계마다 레포에서 실제로 무엇을 하는지 표로 붙였습니다. "한 번에 환경변수 하나만 바꾼다"는 원칙도 거기 적어 두었습니다.

> **평가 포인트**: 미션의 목적을 "프로그램을 고치는 것"이 아니라 "증거 기반으로 원인을 설명하고 소통하는 것"으로 이해하고 있는지 확인한다.

## 2. 요구사항 정리 (5분)

**평가자**: 최종 제출물이 정확히 뭔지 정리해 볼까요?

**발표자**: GitHub Issue 형식 리포트 3건입니다. OOM Crash, CPU Latency, Deadlock 각각 하나씩이고, 리포트마다 아래 네 섹션이 들어갑니다.

| 섹션 | 들어갈 내용 |
|---|---|
| 1. Description | 어떤 현상이, 언제, 어떤 조건에서 발생했는가 |
| 2. Evidence & Logs | `05-monitor-app-resources.sh` 관제 데이터, 앱 로그 핵심 구간, `ps`/`top` 출력 |
| 3. Root Cause Analysis | 증거 기반 원인 분석 + 관련 OS 동작 원리 |
| 4. Workaround & Verification | 어떤 환경변수를 어떻게 바꿨는지, Before & After |

**평가자**: 케이스별 필수 증거도 따로 있었죠?

**발표자**: 네.

| 케이스 | 필수 증거 | 바꾼 환경변수 |
|---|---|---|
| OOM | 관제 데이터의 메모리 상승 수치, `Memory limit exceeded`/`SELF-TERMINATED` 로그, 최소 2회 실행 비교 | `MEMORY_LIMIT` 100 → 256 |
| CPU | `top`/`ps`/관제로 본 CPU 상승 구간, `WATCHDOG … SIGTERM` 종료 로그 | `CPU_MAX_OCCUPY` 90 → 50 |
| Deadlock | PID 존재, `top -H`/`ps -L`로 CPU·MEM 정체, 마지막 `WAITING … BLOCKED` 로그, 스레드/락 대기 추론 | `MULTI_THREAD_ENABLE` true → false |

**평가자**: 앱을 실행하기 위한 사전 조건도 까다로웠던 것 같은데요.

**발표자**: 조건이 하나라도 안 맞으면 부트 시퀀스 6단계 중 하나에서 실패합니다. root가 아닌 일반 사용자로 실행해야 하고, `AGENT_HOME`과 하위 경로(`upload_files`, `api_keys`, 로그 디렉터리)가 있어야 하고, `secret.key` 내용이 `agent_api_key_test`여야 하고, 포트 15034를 바인딩할 수 있어야 합니다. 이걸 `02-provision-runtime.sh`로 자동화했고, 실제 로그에서 `[1/6]`~`[6/6]`이 모두 `[OK]`로 나옵니다.

> **평가 포인트**: 필수 증거 목록을 정확히 알고 있는지, 그리고 그 목록이 실제 리포트에 반영됐는지를 이후 파트에서 대조한다.

**평가자**: 실행 흐름을 순서대로 말해 볼래요?

**발표자**:

1. 호스트에서 `bash scripts/00-run-all-experiments.sh`를 실행합니다.
2. 00이 01을 부르고, 01이 `codyssey-b1-2-lab` 컨테이너를 만들고(없을 때만) root로 02와 03을 실행합니다.
3. 00이 `experiment-cases.conf`를 한 줄씩 읽어 케이스마다 `docker exec -u agentuser -e 변수=값 ... 04-run-experiment-case.sh <케이스>`를 실행합니다.
4. 04는 환경변수 스냅샷 저장 → 앱, 05 모니터, 07 시스템 도구 스냅샷 실행 → 종료 대기(필요하면 `RUN_TIMEOUT`) → 종료 코드 기록 → 모니터 로그 복사 → 06으로 CSV·스니펫 생성까지 진행합니다.

**평가자**: 컨테이너를 만들 때 `--platform linux/amd64`를 준 이유는요?

**발표자**: 바이너리가 x86-64 ELF인데 제 Mac은 Apple Silicon(arm64)입니다. 플랫폼을 지정하지 않으면 arm64 Ubuntu가 떠서 바이너리를 실행할 수 없습니다.

**평가자**: 왜 굳이 `agentuser`를 따로 만들었어요?

**발표자**: 앱이 root 실행을 거부하기도 하지만, 최소 권한 원칙 때문입니다. 서비스 프로세스가 탈취되더라도 피해 범위가 그 계정으로 한정되고, 15034처럼 1024 이상 포트는 일반 사용자도 바인딩할 수 있어서 root가 필요 없습니다. [05-study.md](./05-study.md)에 정리해 두었습니다.

**평가자**: 모니터는 `agentuser`로 도는데, `ufw status`는 root만 볼 수 있잖아요. `FIREWALL` 값은 어떻게 찍어요?

**발표자**: 03이 root로 방화벽을 켠 뒤 상태를 `runtime/firewall-status.txt`에 써 두고, 05는 그 파일을 읽습니다. 처음에는 02가 이 파일을 썼는데, 02가 방화벽을 켜기 전에 실행돼서 항상 `inactive`가 기록되는 문제가 있었습니다. 03에서 켠 뒤 기록하도록 옮겼고, 이 과정은 [06-troubleshooting.md](./06-troubleshooting.md)에 정리했습니다.

**평가자**: `05-monitor-app-resources.sh` 한 줄에 뭐가 찍히는지 보여 주세요.

**발표자**: OOM Before의 첫 줄입니다.

```text
[2026-10-28 16:17:00] PID:1110 PPID:1095 STATE:SN+ ELAPSED:00:01 THREADS:1 PROC_CPU:17.3% PROC_MEM:0.3% RSS:25592KB SYS_CPU:4.1% SYS_MEM:13.4% DISK_USED:4% PORT:15034 FIREWALL:active CMD:/workspace/bin/agent-leak-app-x86 /workspace/bin/agent-leak-app-x86
```

프로세스 지표(PID, 상태, 스레드 수, CPU, RSS)와 시스템 지표(SYS_CPU, SYS_MEM, DISK)를 같은 줄에 남겨서, 특정 프로세스 문제인지 시스템 전체 문제인지를 한 줄로 비교할 수 있게 했습니다. `THREADS`와 `STATE`는 Deadlock 진단에 썼습니다.

**평가자**: 그 줄에서 RSS는 구체적으로 어떻게 얻어요? 나중에 시계열로는 어떻게 바꾸고요?

**발표자**: 다섯 단계입니다.

1. `ps aux | grep agent-leak-app-x86 | sort -k6 -nr`로 같은 이름 프로세스 중 6번째 열(RSS)이 가장 큰 것을 실제 앱 PID로 고릅니다. 부트로더도 같은 이름이라 이렇게 골라야 합니다.
2. `ps -p <PID> -o ppid=,stat=,etime=,%cpu=,%mem=,rss=,args=`로 칸 이름 없이 한 줄을 받아서 `read`로 변수에 나눠 담습니다. RSS 단위는 KB입니다.
3. 비교용으로 `free`에서 시스템 메모리 사용률을 계산해 `SYS_MEM`으로 같은 줄에 붙입니다.
4. `printf`로 `[시각] PID:… RSS:…KB …` 한 줄을 `monitor.log`에 추가합니다. 10MB를 넘으면 파일을 돌려서 보관합니다.
5. 실험이 끝나면 06이 `gawk`의 `match($0, /RSS:([0-9]+)KB/)` 같은 정규식으로 줄마다 값만 뽑아 CSV를 만듭니다.

그 CSV에서 시각별 RSS 차이를 보면 3초마다 +25,604KB이고, 이 시점을 앱 로그 `Current Heap` 시각과 맞춰 봤습니다.

**평가자**: `STATE:SN+`는 각각 뭔가요?

**발표자**: `S`는 대기(sleep), `N`은 낮은 우선순위(nice)입니다. 앱 로그에 `[SafetyGuard] Process priority lowered (nice=10)`가 찍히는데, 그 결과가 그대로 드러난 겁니다. `+`는 포그라운드 프로세스 그룹이라는 뜻인데, 종료 배너를 수집하려고 앱을 `script`로 가상 터미널에 붙여 실행했기 때문에 생겼습니다.

**평가자**: `PID:1110`인데 run 로그에는 `App started (PID: 1091)`이에요. 왜 달라요?

**발표자**: 1091은 앱을 감싼 `script` 프로세스입니다. 그 아래에 PyInstaller 부트로더(1095)가 있고, 실제 앱은 부트로더의 자식인 1110입니다. 07 스크립트가 같은 실행 중에 남긴 `ps -ef` 출력에 이 부모-자식 관계가 그대로 찍혀 있습니다. 이름이 같아서 모니터는 RSS가 가장 큰 프로세스를 실제 앱으로 고릅니다. [01-concepts.md](./01-concepts.md#부모와-자식-프로세스)에 그림으로 정리했습니다.

**평가자**: `INTERVAL=1`인데 로그 타임스탬프는 16:17:00, 17:02, 17:04처럼 2초 간격이에요.

**발표자**: 루프 안에서 `top -bn1`, `ss`, `free`, `df`를 매번 실행하고 그 뒤에 `sleep 1`을 하기 때문에, 실제 주기는 "수집 시간 + 1초"가 됩니다. 특히 `top -bn1`이 CPU 사용률을 계산하느라 시간이 걸립니다. 이 차이 때문에 OOM에서 마지막 할당이 관제에 안 잡혔는데, 그건 OOM 파트에서 말씀드리겠습니다.

> **평가 포인트**: 남이 이 레포만 보고 똑같이 재현할 수 있는가? 스크립트별 역할과 실행 주체(호스트/root/agentuser)를 구분해 설명할 수 있는가?

## 4. 실험 ① OOM (10분)

### 4-1. 현상

**평가자**: OOM 실험부터 볼게요. 무슨 일이 있었나요?

**발표자**: `MEMORY_LIMIT=100`으로 실행했더니 부트 체크는 모두 통과했는데 약 11초 뒤에 이런 로그를 남기고 종료됐습니다.

```text
2026-10-28 16:17:10,625 [INFO] [MemoryWorker] Current Heap: 100MB
2026-10-28 16:17:10,626 [CRITICAL] [MemoryGuard] Memory limit exceeded (100MB >= 100MB) / (Recommend Over 256MB)
2026-10-28 16:17:10,626 [CRITICAL] [MemoryGuard] Self-terminating process 1110 to prevent system instability.

>>> [SYSTEM] SELF-TERMINATED (Memory Limit Exceeded) <<<
```

run 로그에는 `Exit code: 137 (SIGKILL)`이 남았습니다.

### 4-2. 증거

**평가자**: 메모리가 늘어났다는 증거는요?

**발표자**: 관제 RSS를 시계열 CSV로 뽑아서 앱 로그와 시각을 맞췄습니다.

| 관제 시각 | RSS (KB) | 직전 앱 로그 Heap |
|---|---|---|
| 16:17:00 | 25,592 | (할당 전) |
| 16:17:02 | 51,196 | 25MB (17:01.551) |
| 16:17:06 | 76,800 | 50MB (17:04.575) |
| 16:17:08 | 102,404 | 75MB (17:07.596) |
| 16:17:10 | 102,404 | 75MB (100MB 할당은 17:10.625) |

RSS가 약 3초마다 25,604KB씩 계단식으로 올라가고 한 번도 내려가지 않습니다. 증가 시점이 `Current Heap` 로그와 맞습니다. 같은 실행에서 07 스크립트가 남긴 `ps -L` 출력도 RSS 25,592 → 76,800 → 102,404KB로 같은 값이고, `top` 순간 CPU는 0.0%였습니다.

**평가자**: 마지막 RSS가 102,404KB, 약 100MB인데 Heap도 100MB예요. 같은 값인가요?

**발표자**: 아닙니다. 할당 전부터 RSS가 약 25MB였습니다. 이건 앱 자체가 쓰는 기본 메모리이고, CPU 실험처럼 누수가 없는 케이스에서도 RSS가 25,608KB 근처로 유지됩니다. 그래서 마지막 샘플 102,404KB는 "기본 25MB + Heap 75MB"입니다. 100MB 할당은 16:17:10,625에 일어났고 1ms 뒤에 종료됐는데, 모니터의 마지막 샘플은 그보다 앞이었습니다. 샘플링 주기(약 2초)보다 짧은 사건은 관제에 안 잡힌다는 예입니다. After도 같아서, 마지막 RSS 281,636KB는 "25MB + Heap 250MB"이고 275MB 할당 순간은 찍히지 않았습니다.

**평가자**: 시스템 전체에는 어떤 영향이 있었나요?

**발표자**: `SYS_MEM`은 13.1~14.6%로 거의 변화가 없었고 `PROC_MEM`도 최대 1.2%였습니다. 컨테이너 메모리가 넉넉해서 100MB 누수가 시스템 전체에 영향을 주기 전에 MemoryGuard가 먼저 종료시켰습니다. `SYS_CPU`도 2~4%대로 안정적이어서 CPU 문제는 아니라고 판단했습니다.

### 4-3. 원인 분석

**평가자**: 원인은 뭐라고 보나요? 관측 사실과 추론을 나눠서 말해 주세요.

**발표자**:

- **관측 사실**: RSS가 25MB 단위로 증가만 하고 감소하지 않는다. 증가 시점이 `MemoryWorker`의 Heap 로그와 일치한다. Heap이 `MEMORY_LIMIT`에 도달한 직후 `MemoryGuard`가 종료 로그를 남기고, 종료 코드는 137이다.
- **추론**: `MemoryWorker`가 25MB짜리 데이터를 만든 뒤 참조를 계속 들고 있어서 GC가 회수하지 못하는 Heap 메모리 누수다. 커널 OOM Killer가 아니라 앱 내부 정책인 MemoryGuard가 스스로 SIGKILL로 종료했다.

**평가자**: SIGKILL이라는 건 어떻게 확인했어요? 로그에는 `Self-terminating`만 있잖아요.

**발표자**: 처음엔 확인을 못 했습니다. 04 스크립트가 `wait "$APP_PID" || true`로 종료 코드를 버리고 있었거든요. 종료 코드를 저장하도록 고친 뒤 137이 나왔고, 137은 128 + 9, 즉 9번 신호 SIGKILL입니다. 커널 OOM Killer도 SIGKILL을 쓰지만, 바로 앞에 MemoryGuard 로그가 있고 시스템 메모리가 14% 수준이라 커널이 개입할 상황이 아니었습니다.

**평가자**: 그런데 MemoryGuard는 왜 굳이 앱을 죽여요? 메모리가 넉넉하면 그냥 두면 되잖아요.

**발표자**: 누수는 저절로 멈추지 않기 때문입니다. 그대로 두면 결국 RAM이 차고, 그 전에 스왑이 시작되면서 서버 전체가 느려집니다. RAM이 바닥나면 커널 OOM Killer가 점수를 매겨 종료할 프로세스를 고르는데, 누수를 일으킨 앱이 아니라 DB나 sshd 같은 다른 중요한 프로세스가 고를 수도 있습니다. MemoryGuard는 그 전에 한도에서 자기 자신만 내려서 피해를 한 프로세스로 묶고, 종료 로그로 원인을 남깁니다. 이번 실험에서 `SYS_MEM`이 14% 수준일 때 종료된 것도 그 때문입니다.

**평가자**: 왜 Stack이 아니라 Heap에서 누수가 나죠?

**발표자**: Stack은 함수가 반환되면 자동으로 정리됩니다. Heap은 동적으로 만든 객체가 저장되는 곳이라, 누군가 참조를 들고 있는 한 GC가 회수할 수 없습니다. 이 앱은 Python 기반이니 전역 리스트에 계속 append만 하는 구조일 가능성이 큽니다.

**평가자**: RSS와 VSZ 차이는요?

**발표자**: VSZ는 프로세스가 예약한 가상 주소 공간 전체이고, RSS는 그중 실제 물리 RAM에 올라간 크기입니다. 할당만 하면 VSZ가 먼저 늘고, 실제로 쓰는 순간 페이지 폴트가 나면서 물리 페이지가 매핑되어 RSS가 늘어납니다. 그래서 누수 진단은 RSS로 했습니다.

### 4-4. 조치와 검증

**평가자**: 어떤 조치를 했나요?

**발표자**: 앱이 `Recommend Over 256MB`라고 안내해서 `MEMORY_LIMIT`만 100에서 256으로 올렸고, 다른 변수는 그대로 두었습니다.

| 지표 | Before (`MEMORY_LIMIT=100`) | After (`MEMORY_LIMIT=256`) |
|---|---|---|
| 생존 시간 | 약 11초 (16:16:59 ~ 16:17:10) | 약 32초 (16:17:14 ~ 16:17:46) |
| 시작 RSS | 25,592 KB | 25,596 KB |
| 마지막 RSS (관제) | 102,404 KB | 281,636 KB |
| 종료 시 Heap | 100MB | 275MB |
| 증가 속도 | 25MB / 약 3초 | 25MB / 약 3초 |
| 종료 코드 | 137 (SIGKILL) | 137 (SIGKILL) |

생존 시간은 약 3배로 늘었지만 증가 속도는 똑같고, 같은 원인으로 다시 종료됐습니다. 그래서 환경변수 조정은 임시 조치이고 근본 해결이 아니라고 결론 냈습니다.

**평가자**: 한도가 256인데 275에서 종료됐어요. 왜죠?

**발표자**: 25MB 단위로 할당하니까 250MB일 때는 256 미만이라 통과하고, 다음 할당으로 275MB가 된 뒤에야 `>=` 조건에 걸립니다. MemoryGuard가 할당 전이 아니라 할당 후에 검사한다는 뜻이고, 실제 사용량은 한도보다 최대 한 청크(25MB)까지 넘칠 수 있습니다.

**평가자**: 생존 시간을 미리 계산할 수 있어요?

**발표자**: 첫 할당이 시작 후 약 2초, 이후 약 3.03초 간격입니다.

- 필요한 할당 횟수 = ⌈LIMIT / 25⌉
- 생존 시간 ≈ 2 + (⌈LIMIT / 25⌉ − 1) × 3.03초

100MB는 4회라 약 11초, 256MB는 11회라 약 32초로 실측과 맞습니다.

**평가자**: 그럼 512로 올리면 약 63초겠네요?

**발표자**: 이 앱에서는 아닙니다. 부팅 검사에서 `MEMORY_LIMIT`이 256 이하일 때만 `WARNING`이고, 512는 `OK`입니다. 그러면 메모리 누수 시나리오가 선택되지 않습니다. 실제로 CPU After와 Deadlock After 케이스가 `MEMORY_LIMIT=512`였는데, Heap이 525MB까지 오른 뒤 `MEMORY RECOVERED (Cache Cleared)`로 50MB까지 회수됐습니다. 그래서 공식은 누수 시나리오가 선택된 경우에만 맞습니다.

**평가자**: 근본 해결책은요?

**발표자**: 다 쓴 데이터의 참조를 끊는 것(`del`, 스코프 종료), 캐시라면 LRU처럼 크기 제한을 두는 것, 운영 측면에서는 80% 구간에서 미리 알림을 보내고 정리하는 것입니다. 바이너리 디컴파일은 금지라서 코드 수정은 제안으로만 남겼습니다.

> **평가 포인트**: 리포트의 모든 숫자가 `evidence/oom/` 원본 파일로 추적되는가? 관제 값과 앱 로그 값의 차이를 설명할 수 있는가?

## 5. 실험 ② CPU 과점유 (8분)

**평가자**: CPU 실험 조건부터 말해 주세요.

**발표자**: `MEMORY_LIMIT=512`, `MULTI_THREAD_ENABLE=false`로 고정해서 메모리 종료와 Deadlock이 끼어들지 않게 하고, `CPU_MAX_OCCUPY`만 90(Before)과 50(After)으로 바꿨습니다. 두 케이스 모두 `RUN_TIMEOUT=120`을 걸었습니다.

**평가자**: Before 로그를 보여 주세요.

**발표자**:

```text
2026-10-28 16:17:53,385 [INFO] [CpuWorker] Started. Maximum CPU Limit: 90%
2026-10-28 16:17:53,388 [INFO] [CpuWorker] Current Load: 5.00%
2026-10-28 16:17:56,527 [INFO] [CpuWorker] Current Load: 12.65%
...
2026-10-28 16:18:12,126 [INFO] [CpuWorker] Current Load: 43.03%
2026-10-28 16:18:15,246 [INFO] [CpuWorker] Current Load: 51.54%
2026-10-28 16:18:15,351 [CRITICAL] [CpuWorker] CPU Threshold Violated! (51.540000000000006%).

>>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<
```

약 3초마다 부하가 오르다가 약 24초 만에 종료됐고, 종료 코드는 `143 (SIGTERM)`입니다.

**평가자**: 143이면 타임아웃으로 죽인 것과 구분이 안 되지 않나요? 타임아웃도 SIGTERM을 보내잖아요.

**발표자**: 그래서 run 로그에 `Exit mode`를 같이 남겼습니다. Before는 `앱 자체 종료`로 120초 전에 끝났고, After는 `App still running after 120s` 뒤에 `RUN_TIMEOUT(120s) 강제 종료`입니다. Before의 SIGTERM은 앱 내부 Watchdog이 보낸 것이고, 배너도 그 직후에 찍혀 있습니다.

**평가자**: 처음부터 WATCHDOG 배너가 잘 찍혔나요?

**발표자**: 아니요. 처음 수집한 로그는 `CPU Threshold Violated` 줄에서 끝났습니다. 원인은 출력 버퍼링이었습니다. 출력이 파일로 리다이렉트되면 블록 단위로 버퍼에 모였다가 한꺼번에 써지는데, 버퍼를 비우기 전에 SIGTERM으로 종료되면서 배너가 사라졌습니다. `script`로 가상 터미널을 붙여 줄 단위로 출력되게 바꾸고, 종료 코드도 기록하게 해서 다시 수집했습니다. 같은 이유로 OOM의 `SELF-TERMINATED` 배너도 그때 처음 잡혔습니다. 자세한 과정은 [06-troubleshooting.md](./06-troubleshooting.md)에 있습니다.

**평가자**: 같은 시간대 `top`/`ps`/관제는 어땠어요?

**발표자**: 앱은 부하가 5%에서 51.54%로 오른다고 하는데, 관제의 `PROC_CPU`는 시작 직후 17.8%에서 1.9%까지 오히려 내려갔습니다. `SYS_CPU`도 2~4%였습니다. 같은 실행에서 07 스크립트가 3초마다 남긴 `top -H` 순간 CPU는 0~3.9%였고, 누적 CPU 시간(`TIME+`)은 22초 동안 0.15초만 늘었습니다.

**평가자**: 왜 그렇게 나왔을까요?

**발표자**: `ps -o %cpu`는 순간 사용률이 아니라 "시작부터 지금까지 쓴 CPU 시간 ÷ 경과 시간", 즉 누적 평균입니다. 시작 직후 부팅 작업으로 CPU를 좀 쓰고 그 뒤로 거의 쉬면 값이 점점 작아집니다. 그래서 `top -H -b -n 2 -d 1 -p <PID>`로 1초 간격 두 번 측정한 뒤 두 번째 값, 즉 직전 1초의 순간값을 같이 기록했습니다. 그것도 0~3.9%였습니다.

**평가자**: CPU를 볼 때 쓴 명령이 여러 개던데, 옵션까지 하나씩 구분해 볼래요?

**발표자**:

| 명령 | 옵션 | 무엇을 보나 |
|---|---|---|
| `ps -p <PID> -o %cpu` | `-p` 대상 PID만, `-o` 출력할 칸 지정 | 시작부터의 평균 사용률 (05 관제 `PROC_CPU`) |
| `top -bn1` | `-b` 텍스트로 출력, `-n1` 한 번만 | `Cpu(s)` 줄의 유휴값으로 시스템 전체 사용률 계산 (05 관제 `SYS_CPU`) |
| `top -H -b -n 2 -d 1 -p <PID>` | `-H` 스레드별, `-n 2 -d 1` 1초 간격 2회, `-p` 대상만 | 2회차의 스레드별 순간 `%CPU`와 누적 `TIME+` (07) |
| `ps -L -p <PID> -o tid,stat,%cpu,wchan` | `-L` 스레드마다 한 줄 | 스레드 상태, 평균 `%CPU`, 커널 대기 함수 (07) |

`top`을 두 번 재는 이유는 1회차에는 비교할 이전 값이 없어서 순간값으로 믿기 어렵기 때문입니다. 그리고 `%CPU`는 모두 코어 1개 기준이라, 이 컨테이너(8코어)에서 프로세스 하나는 최대 800%까지 나올 수 있고, 스레드 하나는 최대 100%입니다.

**평가자**: 그럼 실제로는 CPU를 거의 안 썼다는 뜻 아닌가요?

**발표자**: 맞습니다. 순간값으로 봐도 낮으니까, `Current Load`는 실제 CPU 사용률이 아니라 앱이 Watchdog 판단용으로 계산하는 값으로 추정합니다. 그래서 리포트에는 "앱 내부 지표"와 "OS 측정값"을 구분해서 적었고, CPU 장애 판단의 근거는 앱 로그의 Load 추이, WATCHDOG 배너, 종료 코드로 잡았습니다. README 검증표에는 앱 로그 Load 상승 구간과 같은 구간의 `top`/`ps` 출력을 나란히 제시했습니다.

**평가자**: `top` 측정은 본 실험이랑 같은 실행이에요?

**발표자**: 네. 처음에는 같은 조건으로 앱을 따로 띄워 측정했는데, 본 실험과 날짜가 달라 증거로 약했습니다. 그래서 `07-capture-system-tools.sh`를 만들어 04가 앱과 같이 백그라운드로 실행하게 했고, 6개 케이스를 다시 돌려 `evidence/cpu/before-systools.log`에 같은 실행의 `ps -ef`, `ps -L`, `top -H` 출력을 남겼습니다. 마지막 회차는 `top`이 1초 측정하는 사이 Watchdog이 앱을 종료해서 출력이 비어 있는데, 그것도 그대로 두었습니다.

**평가자**: 한도가 90%인데 51.54%에서 위반이라고 나왔어요.

**발표자**: 다른 실행에서도 55.10%, 51.29%, 50.36%, 52.05%, 58.93%처럼 항상 50%를 처음 넘은 직후에 종료됐습니다. 앱이 `Recommend Under 50%`라고 경고하는 걸 보면, 설정값과 상관없이 내부 기준 50%로 판단하는 것으로 봅니다. 설정값과 실제 기준이 다른 건 리포트의 근본 해결 제안에 적었습니다.

**평가자**: 실제 서버였다고 치고요. CPU를 많이 쓰는 프로세스 하나를 Watchdog이 죽이는 게 왜 보호가 돼요? 그 서비스는 멈추잖아요.

**발표자**: CPU 시간은 스케줄러가 나눠 주는 공유 자원이라서입니다. 한 프로세스가 코어를 계속 쥐면 실행 대기열에 선 다른 프로세스의 차례가 늦어지고, 서버 전체 응답이 느려집니다. `nice`로 우선순위를 낮춰도 실행할 일이 남은 프로세스는 계속 몫을 가져가요. 비율만 바뀌지 실행이 막히지는 않습니다. 문제 프로세스 하나를 내리면 그 코어 시간이 바로 다른 프로세스에 돌아가고, 서비스는 재시작으로 복구할 수 있습니다. 전체가 느려지는 것보다 하나가 재시작하는 쪽이 피해가 작다는 판단입니다. Watchdog이 SIGKILL이 아니라 SIGTERM을 쓰는 것도 정리할 기회를 주려는 것으로 봅니다.

**평가자**: After는요?

**발표자**: `CPU_MAX_OCCUPY=50`으로 바꾸니 부팅 판정이 `OK`가 되고 `Healthy System Monitoring` 시나리오가 선택됐습니다. 부하가 50%에 닿으면 `Peak reached (50.00%). Starting cooldown...`으로 5%까지 내려갔다가 다시 오르는 걸 반복했고, 120초 동안 종료되지 않았습니다.

> **평가 포인트**: 측정 도구가 무엇을 측정하는지(누적 평균 vs 순간값) 설명할 수 있는가? 같은 종료 코드를 무엇으로 구분했는가? 설명되지 않는 데이터를 숨기지 않고 한계로 제시하는가?

## 6. 실험 ③ Deadlock (7분)

**평가자**: Deadlock 조건은요?

**발표자**: `MEMORY_LIMIT=512`, `CPU_MAX_OCCUPY=50`으로 고정해서 메모리와 Watchdog 종료가 끼어들지 않게 하고, `MULTI_THREAD_ENABLE`만 true(Before)와 false(After)로 바꿨습니다. Deadlock이면 앱이 스스로 끝나지 않으니까 `RUN_TIMEOUT=120`을 걸었습니다.

**평가자**: OOM 실험도 `MULTI_THREAD_ENABLE=true`였는데 그땐 Deadlock이 안 났잖아요.

**발표자**: 앱은 부팅 때 WARNING인 항목에 맞는 시나리오 하나만 고릅니다. OOM 실험은 MEMORY와 THREAD가 동시에 WARNING이었는데 메모리 시나리오가 실행됐고, 관제에서도 스레드가 1개였습니다. 그래서 Deadlock 실험은 메모리를 512로 올려 THREAD만 WARNING이 되게 했습니다.

**평가자**: 무슨 일이 있었나요?

**발표자**: 기동 약 9초 뒤에 이 로그를 마지막으로 멈췄습니다.

```text
2026-10-28 16:20:31,493 [INFO] [AgentWorker][Worker-Thread-1] LOCK ACQUIRED: [Shared_Memory_A]. (Holding...)
2026-10-28 16:20:31,493 [INFO] [AgentWorker][Worker-Thread-2] LOCK ACQUIRED: [Socket_Pool_B]. (Holding...)
2026-10-28 16:20:33,509 [INFO] [AgentWorker][Worker-Thread-1] WAITING for [Socket_Pool_B]... (Status: BLOCKED)
2026-10-28 16:20:33,509 [INFO] [AgentWorker][Worker-Thread-2] WAITING for [Shared_Memory_A]... (Status: BLOCKED)
```

이후 120초 시점까지 약 110초 동안 로그가 한 줄도 없었고, run 로그에 `App still running after 120s`가 남았습니다.

**평가자**: 처음 "응답이 없다"는 걸 봤을 때 무엇부터 확인했어요? 순서대로요.

**발표자**: 다섯 단계로 좁혀 갔습니다.

1. `ps -ef | grep agent-leak-app-x86`: PID가 남아 있는지 봅니다. 없으면 죽은 장애라서 종료 코드와 종료 로그 쪽으로 갑니다. 이번엔 남아 있었습니다.
2. 앱 로그 `tail`: 마지막 기록 시각이 계속 그대로인지 봅니다. 16:20:33 이후 멈춰 있었습니다.
3. `top -H -b -n 2 -d 1 -p <PID>`: 스레드별 순간 CPU를 봅니다. 높고 `R` 상태면 무한 루프, 0%면 무언가를 기다리는 겁니다. 3개 모두 0.0%였고 `TIME+`도 그대로였습니다.
4. `ps -L -o tid,stat,wchan`: 어디서 기다리는지 봅니다. `do_select`면 그냥 쉬는 중이고, `futex_wait`면 Lock 대기입니다. 3개 모두 `futex_wait`였습니다.
5. 로그의 `LOCK ACQUIRED`, `WAITING` 줄: 누가 무엇을 쥐고 무엇을 기다리는지 적어서 원이 되는지 확인합니다.

1~2단계로 "살아 있는데 일을 안 한다", 3단계로 "바쁜 게 아니라 기다린다", 4단계로 "Lock을 기다린다", 5단계로 "서로를 기다린다"까지 좁힌 겁니다.

**평가자**: 5단계에서 서로 기다린다는 건 로그로 어떻게 그렸어요?

**발표자**: `grep -E "LOCK ACQUIRED|WAITING" evidence/deadlock/before-app.log`로 Lock 관련 네 줄만 남기고 관계를 적었습니다.

| 로그 | 관계 |
|---|---|
| Thread-1 `LOCK ACQUIRED: [Shared_Memory_A]` | A는 Thread-1이 쥠 |
| Thread-2 `LOCK ACQUIRED: [Socket_Pool_B]` | B는 Thread-2가 쥠 |
| Thread-1 `WAITING for [Socket_Pool_B]` | Thread-1은 B를 기다림 |
| Thread-2 `WAITING for [Shared_Memory_A]` | Thread-2는 A를 기다림 |

화살표로 이으면 Thread-1 → B → Thread-2 → A → Thread-1로 원이 닫힙니다. 이건 로그 문구를 해석한 거라서, OS 쪽 증거로 한 번 더 확인했습니다. 그 뒤로 로그가 110초간 없고, 스레드가 모두 `futex_wait`이고, `TIME+`가 늘지 않았습니다.

**평가자**: "멈췄다"만으로는 Deadlock이라고 할 수 없잖아요. 근거를 하나씩 말해 주세요.

**발표자**:

| 근거 | 증거 |
|---|---|
| PID 유지 | `ps -ef \| grep agent-leak-app-x86` 27회 모두 실제 앱 PID 5734 존재, 120초 시점 `App still running after 120s` |
| 로그 정지 | 마지막 로그 16:20:33 `WAITING ... BLOCKED`, 이후 약 110초 없음 |
| CPU 정체 | `top -H` 순간 CPU 3개 스레드 모두 0.0%, `TIME+`가 16:20:38 ~ 16:22:20 동안 0:00.23에서 고정 |
| 메모리 정체 | RSS 증가 없이 18,500KB에서 고정 |
| 스레드 상태 | `ps -L` 3개 스레드, `STATE:SNl+` 유지 |
| 커널 대기 지점 | 같은 실행의 `ps -L -o ...,wchan`에서 BLOCKED 이후 25회 모두 스레드 3개가 `futex_wait` |
| Lock 순서 | Thread-1은 A → B, Thread-2는 B → A로 서로 반대 |

`futex`는 Linux에서 Lock 대기를 구현하는 커널 기능입니다. BLOCKED 전에는 Worker 스레드가 `do_select`(작업 중 sleep)였다가 BLOCKED 뒤에 `futex_wait`로 바뀌어서, 작업 대기가 아니라 Lock 대기라는 걸 구분할 수 있었습니다.

**평가자**: `wchan`에서 어느 TID가 Thread-1인지는 어떻게 알았어요?

**발표자**: 커널 정보만으로는 구분이 안 됩니다. 메인 스레드는 PID와 같은 TID(5734)이고, 나머지 5899·5900은 스레드 이름이 모두 `agent-leak-app-`으로 같아서 생성 순서로 대응시켰습니다. 리포트에도 추정이라고 적었습니다.

**평가자**: `ps -L`의 `%CPU`는 1.5%에서 0.1%로 줄어드는데, 그건 뭔가요?

**발표자**: `ps`의 `%CPU`는 누적 평균이라 CPU를 안 써도 시간이 지나면 값이 줄어듭니다. 그래서 정체 근거는 `top -H`의 순간값 0.0%와, 누적 CPU 시간 `TIME+`가 100초 동안 그대로라는 점으로 잡았습니다.

**평가자**: Deadlock 4조건으로 설명해 보세요.

**발표자**:

| 조건 | 이 앱에서 | 깨는 방법 |
|---|---|---|
| 상호 배제 | `Shared_Memory_A`, `Socket_Pool_B`는 한 번에 한 스레드만 Lock (`Strict resource locking is enabled`) | 공유 가능한 자원으로 설계 |
| 점유 대기 | Lock 하나를 `Holding...`한 채 다른 Lock 요청 | 필요한 Lock을 한 번에 모두 획득 |
| 비선점 | 상대의 Lock을 강제로 뺏을 수 없음 | `acquire(timeout=...)` 실패 시 보유 Lock 반납 |
| 순환 대기 | Thread-1 → B(Thread-2 보유), Thread-2 → A(Thread-1 보유) | 모든 스레드가 같은 순서로 Lock 획득 |

**평가자**: 네 개 중에 이 앱에서 핵심은 뭐라고 봐요?

**발표자**: 상호 배제와 순환 대기입니다. 상호 배제만 있으면 그냥 순서대로 기다리면 끝납니다. 문제는 두 스레드가 Lock을 서로 반대 순서(A→B, B→A)로 잡아서 기다림이 원을 이룬 거예요. 그래서 가장 간단한 해결도 순환 대기를 깨는 것, 즉 모든 스레드가 A → B 같은 순서로만 잡게 하는 겁니다.

**평가자**: 무한 루프와 Deadlock은 둘 다 "응답 없음"인데 어떻게 구분해요?

**발표자**: CPU를 보면 됩니다. 무한 루프는 계속 계산하니까 CPU가 높고 `R` 상태입니다. Deadlock은 Lock을 기다리며 잠들어 있으니 CPU가 0에 가깝고 `S` 상태입니다. 그래서 "PID는 있는데 CPU가 0이고 로그가 멈췄다"는 조합이 Deadlock의 신호입니다.

**평가자**: After는요?

**발표자**: `MULTI_THREAD_ENABLE=false`로 바꾸니 Lock 경합 로그가 없어지고 `Healthy System Monitoring` 시나리오로 120초 내내 로그가 계속 진행됐습니다. 스레드는 똑같이 3개지만 Worker 2개는 `do_select`(작업 사이 sleep)였고 `TIME+`가 계속 늘었습니다. `futex_wait`는 Worker를 기다리는 메인 스레드뿐이었습니다. 다만 이건 동시 처리를 꺼서 경합을 피한 우회책이고, Lock 순서 문제는 코드에 그대로 남아 있습니다.

> **평가 포인트**: PID 유지, 로그 정지, 자원 정체, 스레드 대기, Lock 순서를 함께 제시해 "단순히 멈췄다"와 Deadlock을 구분했는가?

## 7. 인사이트와 운영 관점 (8분)

**평가자**: 이번 미션에서 얻은 인사이트를 정리해 주세요.

**발표자**:

1. **환경변수 조정은 증상 완화일 뿐이다.** `MEMORY_LIMIT`을 2.56배 올려 생존 시간이 11초에서 32초가 됐지만, 누수 속도(25MB/3초)는 그대로였습니다. 한도가 아니라 증가 기울기를 봐야 합니다.

2. **관제 도구가 무엇을 측정하는지 알아야 한다.** `ps %cpu`는 누적 평균이라 CPU 상승을 보여 주지 못했고, 순간값으로 봐도 앱이 말하는 부하와 달랐습니다. 지표를 믿기 전에 그 지표의 정의부터 확인해야 합니다.

3. **샘플링 주기보다 짧은 사건은 관제에 안 잡힌다.** 마지막 할당과 종료가 1ms 차이라 관제에는 그 직전 값이 남았습니다. 관제 데이터와 앱 로그를 타임스탬프로 맞춰 봐야 전체 그림이 나옵니다.

4. **증거가 안 남는 데도 이유가 있다.** WATCHDOG 배너가 없던 건 앱이 배너를 안 찍어서가 아니라 출력 버퍼가 비워지기 전에 종료됐기 때문이었습니다. 종료 코드처럼 버퍼와 상관없는 증거를 같이 남겨야 합니다.

5. **앱 보호 장치와 OS 보호 장치는 다르다.** MemoryGuard(SIGKILL, 137)와 Watchdog(SIGTERM, 143)은 앱이 스스로 내려가는 장치이고, 커널 OOM Killer와는 다릅니다. Deadlock은 어느 기준도 넘지 않아서 아무도 종료시키지 않습니다.

6. **변수는 하나씩, 환경은 같게.** 6개 케이스를 같은 컨테이너에서 스크립트 한 번으로 연달아 돌려서, 결과 차이를 바꾼 변수 하나로만 설명할 수 있게 했습니다.

**평가자**: 실무에 적용한다면 뭘 가져가겠어요?

**발표자**: 장애가 나면 재시작 전에 `ps -ef`, `ps -L`(`wchan` 포함), `top -H`, 마지막 로그, 환경변수, 종료 코드를 먼저 남기는 습관입니다. `04-run-experiment-case.sh`와 `07-capture-system-tools.sh`처럼 그 수집을 스크립트로 만들어 두면 장애 상황에서도 빠뜨리지 않습니다.

### 7-1. 운영 관점 질문

**평가자**: 이 앱이 실제 서비스였다면, 지금 관제 스크립트로 누수를 종료 전에 알 수 있었을까요?

**발표자**: 못 했을 겁니다. 지금은 값을 기록만 하고, 앱이 종료된 뒤에 로그를 보고 알았습니다. 운영용이라면 이렇게 바꾸겠습니다.

- RSS의 최근 몇 분간 증가량, 즉 기울기를 계산해서 줄지 않고 계속 오르면 경고합니다. 누수는 크기보다 모양으로 먼저 보입니다.
- `MEMORY_LIMIT`의 70%, 85%에서 단계별 경고를 하고, 지금 기울기로 한도까지 남은 시간을 같이 보여 줍니다. 이번 데이터(3초에 25MB)면 100MB 한도까지 약 11초라는 걸 미리 계산할 수 있습니다.
- 실제 주기가 2초로 밀리는 걸 보정하고, 경고는 파일이 아니라 알림으로 보냅니다.
- 같은 김에 순간 CPU, 로그 마지막 기록 시각, `TIME+` 정체도 감시해서 CPU와 교착상태까지 잡게 하겠습니다.

**평가자**: 세 장애 중 서비스에 제일 위험한 건 뭐라고 생각해요?

**발표자**: Deadlock입니다. OOM과 CPU는 보호 장치가 앱을 내려서 적어도 "죽었다"는 신호와 로그가 남고, 서비스 관리자가 재시작할 수 있습니다. Deadlock은 PID가 살아 있고 CPU·메모리가 오히려 조용해서, 프로세스 존재나 자원 사용률만 보는 헬스 체크를 다 통과합니다. 그동안 들어온 요청은 응답 없이 쌓이고요. 예방은 코드에서 Lock 순서 통일과 타임아웃 있는 획득, 운영에서는 실제 요청을 처리해 봐야 통과하는 헬스 체크를 두고 응답이 없으면 재시작하는 겁니다.

**평가자**: 같은 서버에서 OOM이랑 Deadlock이 동시에 터지면요? 뭘 먼저 해요?

**발표자**: 순서는 증거 수집 → OOM → Deadlock입니다.

1. 두 프로세스의 `ps -ef`, `ps -L`(`wchan`), `top -H`, 마지막 로그, 환경변수를 먼저 남깁니다. 재시작하면 사라지는 증거들이고, 몇 초면 끝납니다.
2. OOM을 먼저 처리합니다. 누수는 시간이 갈수록 나빠지고, RAM이 바닥나면 커널 OOM Killer가 상관없는 프로세스까지 죽일 수 있습니다. 교착상태는 멈춘 상태가 유지될 뿐 더 번지지 않습니다.
3. 그다음 Deadlock 쪽 Lock 순서를 확인하고 재시작합니다.

그리고 1단계에서 둘이 같은 프로세스인지도 확인합니다. 교착상태에 빠진 프로세스가 메모리를 쥐고 있어서 OOM이 났을 수도 있으니까요.

**평가자**: 소스를 직접 고칠 수 있었다면요?

**발표자**:

| 장애 | 코드에서 고칠 것 |
|---|---|
| OOM | 다 쓴 데이터는 리스트에서 빼서 참조를 끊고, 캐시는 `deque(maxlen=N)`이나 LRU처럼 크기 상한을 둡니다 |
| CPU | 작업을 잘게 나눠 중간중간 CPU를 양보하고, 설정값(`CPU_MAX_OCCUPY`)이 실제 판단 기준이 되게 고칩니다. 지금은 90으로 설정해도 50에서 종료됩니다 |
| Deadlock | 모든 스레드가 같은 순서로 Lock을 잡게 하고, `acquire(timeout=...)`로 못 잡으면 쥔 Lock을 놓고 재시도하게 합니다 |

README의 "소스 코드를 고칠 수 있다면"에 Lock 순서를 통일한 Python 예시도 넣었습니다.

**평가자**: 처음부터 다시 한다면 뭘 다르게 하겠어요?

**발표자**: 이번에 실제로 막혔던 것 네 가지를 앞당기겠습니다.

1. `top` 순간값과 `wchan`을 처음엔 따로 측정해서 증거로 약했습니다. 처음부터 실험 스크립트에 `ps -ef`, `ps -L`, `top -H` 수집을 넣겠습니다.

**잘한 점**

- 컨테이너 생성부터 6개 케이스 실험, 증거 정리까지 스크립트 하나로 재현할 수 있다.

- 종료 코드로 SIGKILL/SIGTERM을 확인하고, `Exit mode`로 Watchdog 종료와 타임아웃 종료를 구분했다.
- Deadlock을 로그 정지만이 아니라 같은 실행의 `ps -L` `futex_wait`, `top -H` `TIME+` 고정, Lock 순서까지 근거로 판단했다.

- 리포트마다 관측 사실, 추론, OS 원리를 나눠서 썼다.

**보완할 점**

1. 관제 실제 주기가 약 2초라 짧은 사건을 놓친다. `sleep` 시간을 수집 시간만큼 줄이거나, 앱 로그 줄 수를 관제 로그에 함께 기록하는 방법을 고려할 수 있다.
2. `07-capture-system-tools.sh`의 `top` 순간 CPU는 3초마다 1초 구간만 측정한다. 관제(05)의 시계열에 같은 순간값을 넣으면 하나의 CSV로 비교할 수 있다.
